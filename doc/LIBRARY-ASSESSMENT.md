# Оценка библиотеки как основы для проектов

Срез рабочего дерева: 5 сентября 2026 года, версия в `package.json` — `2.16.0`.
Это оценка имеющихся контрактов, исходников и проверок, а не подтверждение публикации версии
или эксплуатации распределённого кластера на разных машинах. Изменения и результаты общего
аудита перечислены отдельно в [COMPREHENSIVE-AUDIT.md](COMPREHENSIVE-AUDIT.md).

Материалы из `experiments/`, `src/`, `type-tests/` и `scripts/` доступны только в repository checkout.
Они указаны обычными путями; ссылки ведут на материалы, включённые в npm-пакет.

## Основной вывод

`wenay-common2` полезна как основа TypeScript-приложения с авторитетным состоянием, командами,
живыми подписками и восстановлением после разрыва связи. В этой модели уже есть связный путь
от локальной логики до нескольких обслуживающих узлов. Пользователь получает больше, чем
набор транспортных утилит: последовательность изменений, снимки, догоняющее чтение, маршруты,
командные receipts и жизненный цикл соединений совместимы между слоями.

Полнота внутри этой модели высокая; полнота готового продукта существенно ниже. Библиотека
не определяет бизнес-инварианты, схему хранения приложения, политику доступа, операционное
развёртывание и межпартиционные операции. Это согласуется с [INTENT.md](INTENT.md) и
[границей динамического runtime](DYNAMIC-RUNTIME.md), а не является недоделкой каждого слоя.

Для ИИ-разработки особенно полезны явные фабрики и фасады: тип можно вывести из реализации,
а поведение проверить через тот же фасад. Основная помеха сейчас — не отсутствие ещё одного
нижнего механизма, а количество вариантов сборки и незавершённая упаковка рекомендованного
старта проекта.

Важная деталь для генератора кода: namespace не равен package subpath. В текущем `exports`
нет `wenay-common2/scale` и `wenay-common2/command`; используются `import {Scale, Command}
from 'wenay-common2'`. Внутренние `src/...` и `lib/...` пути из примеров нельзя автоматически
переносить в приложение как разрешённые экспорты пакета.

## Где остаётся работа приложения

- **Domain:** состав сущностей, допустимые команды, проверки до изменения состояния,
  конфликтующие операции, read policy, правила повторов и внешних эффектов.
- **Host:** конкретный транспорт и его закрытие, идентификация, выдача и проверка credentials,
  ограничение доступных фасадов, выбор текущей write-сессии, persistence adapters.
- **Эксплуатация:** секреты, сеть, процессы, хранение и восстановление, наблюдаемость,
  стратегия обновлений и внешний fencing там, где возможны независимые претенденты на запись.
- **Продукт:** UI, интеграции с платёжными/почтовыми/AI-провайдерами, аудит действий и бизнес-SLA.

Receipt позволяет вернуть результат повтора в поддерживаемом коридоре; сам по себе он не
превращает внешний HTTP-вызов или изменение отдельной БД в exactly-once операцию. Нужно
определить, что происходит между внешним эффектом, записью состояния и сохранением receipt.
Подробные ограничения приведены в [аудите](COMPREHENSIVE-AUDIT.md#оставшиеся-границы).

Read projection также не равна авторизации. В scaffold `readerFacet` формирует удобное
представление, но `serve.reader()` одновременно предоставляет полную replica line. Нельзя
положить секрет в общую реплику и считать его скрытым потому, что HTML-страница читает только
`view`. Это видно в `experiments/wenay-scaffold/template/leader.ts` (repository checkout) и
прямо отмечено в `experiments/wenay-scaffold/README.md` (repository checkout).
Для разных прав чтения нужна отдельная разрешённая публикация состояния либо проверяемая
граница доступа к самой линии; выбор полей только на стороне клиента этого не обеспечивает.

## Постепенное масштабирование: два разных ограничения

**Узлы чтения** распределяют обслуживание подписчиков, снимков и трафика. `createClusterClient`
выбирает replica route, а `createStoreNode` может пересылать команды в authority с исходным
токеном. При этом порядок изменения одной линии по-прежнему задаёт одна authority. Добавление
десяти зеркал не означает десятикратной пропускной способности её команд.
По умолчанию placement сохраняется, пока узел пригоден: появление нового узла не обязано
перенести уже подключённых читателей. Перенос задаётся drain, явным repick или включённым
balance-поведением; это нужно учитывать при оценке эффекта добавленной мощности.

**Разделение записи** означает несколько независимых authorities с разными `storeId`.
Нужны принадлежность данных партиции и адресация команды: например, `tenantId → storeId →
authority`. В [ROADMAP §6](ROADMAP.md#6-scale-tier--the-growth-path-seams-and-presets-not-implementations)
это обозначено как направление и будущий coordinator; текущий `Scale` не предоставляет
готовый автоматический sharding, rebalance данных или межпартиционную транзакцию.

Практический путь:

1. **Local.** Выбрать минимальное состояние и команды. Для отношений использовать ID, а не
   общую изменяемую ссылку в нескольких ветках. Проверить команды и подписки без сети.
2. **Service.** Передать ту же domain-логику в authority, обслужить её фасады через RPC.
   Вывести клиентский тип из фабрики. Для защищённых команд применить
   [канонический auth-контракт](RPC-AUTH.md), затем проверить повтор и reconnect.
3. **Read nodes.** После измерения нагрузки добавить узлы с теми же координатами линии.
   Оставить одного владельца записи; проверить drain, падение, восстановление и lifecycle
   соединений. Для клиента отдельно определить, куда отправлять команды.
4. **Durability / standby.** До требований к восстановлению выбрать сохраняемые данные,
   receipts, backups и их границы. Standby и автоматическое повышение роли не заменяют
   анализ split-brain и внешний механизм исключения двух writers.
5. **Partitions.** Только когда одна authority становится измеренным пределом записи,
   выделить независимые агрегаты и явное правило маршрутизации. Команда должна укладываться
   в одну партицию; межпартиционный процесс получает отдельный прикладной протокол.

Миграция Local → Service в проверенном примере сохраняет реализацию команды, но не обещает
сохранить тот же первоначальный экземпляр локального Store: authority получает своё состояние.
Идентичность клиентского Store и его подписки проверяется уже при смене кластерного маршрута
и reconnect. Это полезное различие между переносимостью domain-логики и тождественностью объектов.

## Как ИИ должен строить проект

1. Прочитать [Store guide](STORE-CONSUMER-GUIDE.md), затем `package.json#exports` и декларации
   нужного entrypoint. Не начинать с обхода всех исходников или с максимального demo.
2. Назвать конкретные границы: domain commands, читаемое состояние, host IO и внешние факты.
   Выбрать один основной подход к данным; не собирать сразу Store, Replicated Map, offline
   helpers и replica set для одного и того же маленького экрана без необходимости.
3. Собрать маленькую domain-фабрику с одним `deps` и выводимым `ReturnType`. Фасад должен
   отражать реальные аудитории. Существующий shared contract использовать через `satisfies`,
   а не переписывать список методов интерфейсом.
4. Взять один ближайший рабочий пример: [Workboard](../replay/workboard-demo.test.ts) для
   команд/списка сущностей, [consumer journey](../oracle/realsocket/store-consumer-journey.spec.ts)
   для смены маршрута, `experiments/wenay-scaffold/examples/rental/service.ts` (repository checkout)
   для правил предметной области. Копировать композицию, проверяя импорт и lifecycle каждого слоя.
5. Добавлять транспорт после локальной проверки. Компилятор должен отвергать неверную команду,
   payload и результат; образец — `type-tests/demo-facade.ts` (repository checkout).
6. Проверить приложение как настоящего потребителя пакета. В репозитории это делает
   `scripts/verify-package-consumer.mjs` (repository checkout): установка tarball вне
   исходников, CJS/ESM types/runtime и browser bundle. Source-import тест не заменяет этот шаг.
7. При росте изменять host-композицию и измерять её. Использовать
   `experiments/wenay-scaffold/multiprocess-check.ts` (repository checkout), но не переносить
   его результат на quorum или сеть из независимых машин без дополнительных проверок.

Для небольшого нового приложения выгоднее начать с 2–3 используемых фасадов, чем пытаться
понять всю библиотеку. Media, Conversation и dynamic runtime стоит подключать по фактической
задаче; их наличие в корневом экспорте не делает их обязательным каркасом каждого проекта.

## Цена освоения и найденные несогласованности

Механизмы достаточно мощные, но читателю приходится различать несколько видов `ready`,
несколько способов следования состоянию, данные и команды, события и replay, host и wire
фасады. Особенно легко ошибиться, если объявить промежуточный `Record<string, any>`: код
компилируется, а связь producer → consumer теряется. Текущий source-derived demo уменьшает
эту проблему, но не отменяет необходимость небольшого рекомендованного стартового шаблона.

Проверенные исправления этой волны:

| Раньше | Теперь | Проверка |
| --- | --- | --- |
| Генератор оставлял source imports и требовал ручного переноса | `experiments/wenay-scaffold/create.mjs` (repository checkout) преобразует копию в существующие package entrypoints; in-repo template остаётся исходным | `experiments/wenay-scaffold/standalone-check.mjs` (repository checkout): внешний каталог, local tarball, strict consumer types, реальные процессы |
| CLI ссылался на отсутствующий README | `experiments/wenay-scaffold/template/README.md` (repository checkout) копируется вместе с кодом | self-check проверяет восемь файлов и подстановку имени |
| Документация называла `directory` и считала leader process будущей работой | `experiments/wenay-scaffold/README.md` (repository checkout) использует `roster` и отделяет готовый leader от будущего browser stand | Сверка с возвращаемым фасадом и существующим main |
| Версия допускала `2.15.0` без требуемого Scale | `experiments/wenay-scaffold/template/package.json` (repository checkout) требует `^2.16.0` | Проверена установка локального dist tarball; публикация этой версии не утверждается |

Остаётся граница архитектуры: roadmap описывает будущий partition coordinator. Несколько
независимых authority сами по себе не задают partition key, маршрутизацию или межпартиционные
правила. [Scaling safety](SCALE-SAFETY.md) фиксирует реальные host seams и ограничения:
локальная роль не является распределённой блокировкой, а fencing внешнего эффекта требует
проверки сертификата непосредственно у принимающего ресурса. Имеющиеся проверки разделения
сети полезны, но не заменяют реализацию настоящего coordinator и его эксплуатационные проверки.
Начальная навигация уже улучшена: [README](../README.md) ведёт к Store guide и аудиту, отдельно
объясняет, что shipped examples — читаемые исходники. Не нужно снова превращать README в
полный API tutorial; самостоятельный старт теперь закреплён проверяемым scaffold.

## Приоритет с наибольшей пользой

Самостоятельный scaffold уже реализован: генерация вне репозитория, установка локального пакета,
строгая проверка source-derived типов и выполнение команды через реальные leader/node процессы.
Повторно используется один process oracle, включая receipt reuse, restart узла и reconnect
существующего consumer Store. Это проверка переносимости, а не публикация генератора в npm.

Три примера по уровням (`examples/README.md`) проверили библиотеку с позиции стартапа: роли и
приватность читаемых линий закрыты view-линиями по аудиториям (уровень 2), внешние эффекты —
намерениями в состоянии с раннером и подписанным вебхуком (уровень 3); итог по слоям — `ROADMAP.md §7`.
Следующий полезный шаг — готовая композиция клиентских read/write-сессий. Durable host preset и настоящий partition coordinator остаются
отдельными работами: их нельзя считать следствием добавления serving nodes.
