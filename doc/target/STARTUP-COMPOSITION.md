# Удобная композиция стартап-проекта

Результат проверки 2026-09-05. Это предложение следующего этапа, не описание
нового публичного API и не дополнительная гарантия текущего релиза.

Первый срез реализован в `examples/rental`: копируемый пакетный consumer, typed client,
HTTP/Swagger и проверяемый restart serving node. Клиент подключается к явно заданному
endpoint. Два сервиса, roster placement, durable authority и изоляция организаций из
приёмки ниже остаются следующими этапами; этот пример их не закрывает.

## Статус 2026-09-06

Срез реализован в трёх примерах (`examples/README.md`): rental (уровень 1), pizzeria (уровень 2:
роли, view-линии по аудиториям, login/signup, панель), apartments (уровень 3: платёжные намерения,
раннер эффектов, подписанный вебхук, устройство-замок, durable-лидер с перезапуском). Из списка ниже
закрыты пункты 2 (схема → валидация, типы, OpenAPI), 3 (storage port в host-примере, срок жизни
receipts описан), 4 (публичное и приватное состояние разделены линиями, проверено на snapshot и
replay). Пункт 1 закрыт вторым срезом: `template/client.ts` (`createServiceClient`: логин и продление,
размещение по ростеру, view-линии как стабильные Store, типизированные команды) — замок в apartments
собран на нём; `rental/rental-client.ts` оставлен ручным как показ механики сырой линии. Там же закрыты
долговечные receipts (`control: {durable}`), версия и `migrate` состояния, платёжный порт с
Stripe-образным адаптером. Пункт 5 (две организации) доказан оракулом `observe/scale-solo.test.ts`,
теперь дополнен `examples/smart-home`: два дома, отдельные Store и процессы-владельцы,
освобождение простаивающих проекций и восстановление клиентов после сбоя. Размещение статическое,
без переноса владельца. Выводы следующего среза — `SMART-HOME-FINDINGS.md`; итог по слоям — `ROADMAP.md §7`.

## Вывод

Библиотека уже содержит рабочие механизмы типизированных вызовов, состояния,
повторного подключения и распределения читателей. Основной пробел для нового
проекта — рекомендованная композиция этих механизмов с небольшим числом решений
на стороне потребителя. Готовность механизмов к релизу не означает завершённость
такого пользовательского пути.

## Подтверждено кодом

- `src/Common/scale/scale-client.ts`: клиент выбирает маршрут и материализует Store,
  но не предоставляет фасад команд. В `experiments/wenay-scaffold/multiprocess-check.ts`
  потребитель ведёт карту RPC-сессий и сам связывает команду с текущим маршрутом.
- `src/server/httpFacadeServer.ts`: методы фасада становятся GET/POST-маршрутами
  с позиционными аргументами. Это HTTP-доступ к вызовам; ресурсная REST-модель
  не выводится автоматически из названий методов.
- `demo/http-openapi.ts`: генератор OpenAPI существует как demo incubator,
  а не стабильный экспорт библиотеки. Rental REST отдельно собирает схемы аргументов,
  bearer middleware и общий документ. Это полезный прототип, но ещё не один готовый адаптер.
- `experiments/wenay-scaffold/template/leader.ts`: preset не передаёт durable storage
  в authority; ядро поддерживает этот порт. `serve.reader()` authority отдаёт полную
  replica line. Добавленный рядом `readerFacet` не ограничивает её содержимое.
- `doc/ROADMAP.md`: разделение записи по `storeId` предусмотрено архитектурно,
  но coordinator и его клиентская композиция остаются будущей работой. Добавление
  serving nodes разгружает обслуживание читателей, а не размножает владельца записи.
- История replay служит восстановлению подписок. Долговременная бизнес-история
  с поиском, страницами и политикой хранения требует отдельного ресурса/контракта.
  Сохранение state также не означает сохранение control line и receipts.

## Следующий минимальный срез

Сначала сделать один внешний пример приложения с двумя domain-фабриками и явными
`deps`. Пример должен использовать только устанавливаемый пакет. Локальный вызов,
удалённый вызов и дополнительные serving nodes должны сохранять прикладной фасад;
сетевые ошибки и свежесть данных при этом остаются видимыми, а не маскируются.

1. Собрать клиентские чтение и команды поверх существующих RPC hub и Scale client.
   У сессии один владелец cleanup; зафиксировать поведение команды при смене маршрута,
   deadline, отмене и неоднозначном результате. Повтор использует тот же requestId,
   но не обещает безусловную однократность выполнения.
2. Из той же предметной схемы получить валидацию, типы и OpenAPI. Проверять также
   ответы и ошибки; не выводить runtime-схемы из стёртых TypeScript-типов.
   Ресурсные HTTP-маршруты задавать отдельными явными метаданными при необходимости.
3. Подключить существующий storage port в host-пример и проверить восстановление
   после завершения процесса. Отдельно показать срок жизни receipts и поведение
   внешнего эффекта при повторе. PostgreSQL-адаптер, если нужен, не является
   автоматическим следствием HTTP-фасада.
4. Явно отделить публичное читаемое состояние от приватного. Проверять доступ
   через фактически выдаваемые wire-фасады, включая snapshot и replay.
5. Показать две независимые линии по организациям. Сначала достаточно явного
   соответствия organization → storeId; автоматический перенос партиций требует
   отдельного проектирования владения, маршрутов и миграции данных.

## Приёмка

- Один и тот же прикладной клиент работает с solo authority и после добавления узлов.
- Смена маршрута во время команды имеет определённый и проверенный результат.
- Неверные команда, вход и результат отвергаются type tests внешнего потребителя.
- Перезапуск восстанавливает обещанные данные; границы подтверждения записи явные.
- Секреты другой организации не появляются ни в snapshot, ни в replay.
- OpenAPI совпадает с реальными запросами, ответами и авторизацией.
- Запуск нового проекта не требует копировать управление RPC-сессиями из oracle.

Сначала проверить эту композицию в примере. После этого обсудить минимальный публичный
фасад и только затем переносить повторяемые части в пакет. Не добавлять второй
runtime, registry или протокол поверх уже существующих механизмов.
