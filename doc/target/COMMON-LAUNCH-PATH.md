# Общий путь запуска: rental и document-processing

Статус: локальный транспорт реализован 2026-09-07; серверный и многопроцессный режимы остаются планом.
Результат и границы проверок: [COMMON-HOST-FINDINGS.md](COMMON-HOST-FINDINGS.md). Публичный API не добавлен.
Цель — одна проверяемая основа запуска при сохранении разных предметных ресурсов.

## Что уже есть

| Граница | Rental | Document processing |
| --- | --- | --- |
| Прикладной ресурс | createServiceLeader из scaffold, команды и views из определения | FileJob host + byte storage + processor |
| Клиент | RPC, чтение через rental-client, команды с requestId | FileJobClient, отдельная HTTP-загрузка bytes |
| HTTP/Socket.IO | Общий приватный http-host + маршруты leader-rental.ts | Тот же http-host + маршруты host.ts |
| Идентификация | Демонстрационный bearer, gated write surface, отдельный node-link | Демонстрационные сессии, owner-проверки HTTP и RPC |
| Хранение | SERVICE_DATA_DIR подключает архивы бизнес/control-линий; проверены restart и копия остановленного сервиса | Файлы, метаданные и задачи в памяти |
| Масштабирование | Дополнительные узлы чтения; запись у одного authority | Один host; распределённого исполнения задач нет |

## Три режима и критерии

| Режим | Пользовательский путь | Проверяемая приёмка |
| --- | --- | --- |
| Локальный | Установить пакет, скопировать пример, запустить, открыть напечатанный URL | Нет внешних ключей; ошибки настроек до приёма запросов; импорт не запускает сервер; close завершается и освобождает порт |
| Один сервер | Задать постоянные ресурсы и identity, запустить ту же бизнес-сборку | Состояние и подтверждённые операции переживают restart; проверено восстановление копии; секреты не генерируются заново без явного режима demo |
| Несколько процессов | Добавить reader или worker, увидеть его готовность и распределение работы | Проверены живые маршруты, лимиты, drain, отказ процесса и исходы операций; read scaling и worker/write scaling измеряются отдельно |

Первый режим реализуем без изменения публичной библиотеки. Второй и третий для документов
требуют отдельного решения о durable tasks; наличие постоянных байтов не закрывает эту задачу.
Backup бизнес-линии без control-линии не доказывает восстановление receipts. Смена владельца
записи требует fencing на ресурсе по `doc/SCALE-SAFETY.md`, не просто выбора нового процесса.

## Первый общий ресурс

Выделен приватный `experiments/wenay-scaffold/resources/http-host.ts` для владения Express,
HTTP и Socket.IO. Только транспортный lifecycle: подготовка → bind → ready → close.
Конфигурация identity, RPC-ключи, CORS, маршруты и domain factory остаются у потребителя.
Ресурс принимает одну deps-структуру; его возвращаемый фасад отделяет control, resource и view.
Названия ниже — эскиз для внутреннего scaffold, не существующий экспорт пакета:

```ts
const transport = createHostResource({host: '127.0.0.1', port, socket: socketOptions})
let product
try {
    product = createProduct(productDeps)
    mountProduct({...transport.resource, product})
    await transport.control.listen()
    // Rental публикует адрес в каталоге после bind.
} catch (error) {
    await Promise.allSettled([
        Promise.resolve().then(function closeProduct() { product?.close() }),
        transport.close(),
    ])
    throw error
}
// transport.resource.{app, io}, transport.view.url(), transport.close()
```

Сначала создавать ресурс и проверять его самостоятельно, затем переводить оба consumer.
Пока код доставки примеров копируется, генератор должен брать ресурс из одного источника;
самостоятельно редактировать сгенерированные копии нельзя. Выпуск отдельного пакета основы
позволит обновлять уже созданные проекты, но имя/контракт пакета — отдельное решение.

## Обязательные проверки первого среза

1. Две независимые сборки в одном процессе, закрытие одной не затрагивает другую.
2. Ошибка product mount и занятый порт освобождают всё уже созданное; сохраняется исходная ошибка.
3. Повторный close разделяет завершение; установлены границы ожидания активных соединений.
4. HTTP и Socket.IO действительно закрыты; повторный bind на тот же порт успешен.
5. Product cleanup вызывается один раз; ошибка cleanup не мешает попыткам закрыть транспорт.
6. RPC-ключи, анонимные поверхности, auth gates и CORS обоих продуктов сохранены.
7. Прежние прикладные сценарии проходят через установленный tarball вне репозитория.

Сигналы ОС и process.exit остаются в исполняемом entrypoint. Общая фабрика не должна
завершать вызывающий процесс. Не объединять эту работу с supervisor дочерних процессов,
очередью задач, выдачей токенов или загрузкой модулей.

## Порядок следующих поставок

1. Общий приватный HTTP-host и два consumer, только локальный режим.
2. Постоянные data/control ресурсы rental и проверяемый backup/restore.
3. Согласованный контракт идентичности FileJob-операций, затем его реализация отдельно.
4. Решение об устойчивом исполнителе задач и атомарном хранении его исходов.
5. Нагрузка: throughput, p95, heap, backlog и время восстановления на фиксированном сценарии.

Измерять время старта и обязательные настройки до/после; целевые числа установить после
базового замера. Не выводить производительность из числа прошедших тестов или количества узлов.
