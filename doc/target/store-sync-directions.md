# Синхронизация сторов: три оси развития (дизайн-заметка, без кода)

Контекст: leader-follower зеркало готово (createStoreFollower, фазы 1-3 плана
store-mirror-plan.md). Обсуждение 2026-07-19: куда это растёт. Задача заметки —
разложить интуиции по осям и привязать к УЖЕ существующим примитивам, чтобы
новые фичи ложились на одни понятия, а не плодили механизмы.

## Ось 1 — Направление истины: «нам говорят» vs «мы смотрим»

Оба направления в библиотеке уже есть в зачатке:

- «Нам говорят» (push-журнал): exposeStoreReplay → syncStoreReplay /
  createStoreFollower. Авторитет нумерует дельты, подписчики применяют.
- «Мы смотрим» (pull-зеркало): createStoreMirror(remote).sync()/syncPatches() —
  зеркало само ходит за состоянием (changed/changedPaths + get), журнала нет.

Недостающее звено — **адаптер внешнего источника истины** (например, БД):
узел-наблюдатель превращает чужую истину в обычную replay-линию — снапшот
как keyframe, изменения (CDC / poll-diff / триггеры) как патчи с seq. Дальше
вся сеть работает без изменений: ей всё равно, кто голова линии.

Ключевой концепт: **origin-адаптер** — «голова линии» это интерфейс
(current() + упорядоченный поток патчей), а не конкретный класс узла:
in-memory авторитетный store (сейчас) | внешняя БД под наблюдением |
другой узел (каскад). Роль узла: origin / derived-origin (следит за внешним,
издаёт линию в сеть) / follower.

Насторожка направления «мы смотрим»: линия — это только ЧТЕНИЕ истины.
Команды через неё в БД не проходят; запись в БД живёт её родным путём (или
отдельным командным адаптером со СВОЕЙ идемпотентностью) — наши receipts
там не действуют. Чтение и запись — два разных порта, не смешивать.

## Ось 2 — Много узлов

- Каскад уже композитен по построению: follower издаёт ТУ ЖЕ линию, что и
  лидер, поэтому follower-of-follower работает без нового кода. Демо уже
  двуххоповое: leader → follower → браузер.
- N фолловеров на одном лидере = просто N клиентов; упор — в fan-out лидера.
  Дерево снимает нагрузку: 1 → K → K² (каждый уровень раздаёт следующему).
- Проектировать при реализации:
  - epoch должен ехать В САМОЙ линии (обобщение фазы 4 на дерево: promote
    в середине дерева обязан быть виден вниз по каскаду);
  - лаг per hop — status.seq уже есть у каждого фолловера, дерево = цепочка
    этих статусов;
  - анти-цикл: узел не должен подписаться сам на себя через цепочку —
    линии нужен originId (см. дескриптор ниже), совпадение = отказ.

## Ось 3 — Виды передачи: данные vs источник

Уже есть три способа доставки, их надо назвать и оформить как выбор:

1. **Поток данных** (replay-каскад) — узел проксирует байты подписчикам. Сейчас.
2. **Ссылка на источник** — узел отдаёт не данные, а «источник вон там»;
   подписчик подключается к источнику сам. Переключение маршрута без дыр уже
   умеет syncStoreReplayRoute (gap-free по seq) — это ровно философия
   route-coordinator relay ⇄ direct. Родня пункту «оптимизация маршрута»
   из Отложено в store-mirror-plan.md.
3. **По запросу** (pull) — не стримить вовсе: снапшот/дифф когда спросят.
   Это createStoreMirror.sync как режим доставки для редко-читающих узлов.

Ключевой концепт: **дескриптор источника** — маленький объект
{originId, epoch, seq, маршруты: [прямой адрес, «через меня»]}. Узел может
раздавать многим дешёвый дескриптор вместо дорогих данных; потребитель сам
выбирает транспорт (прямой, через посредника, pull). Данные едут только по
выбранному пути. Дескриптор же решает анти-цикл (originId) и даёт fork-choice
при promote (epoch).

## Что не делаем сейчас

Ничего из этого не кодим до фазы 4 (promote) и первого реального сценария.
Порядок, когда дойдём: (3.2) ссылка на источник — самое дешёвое, примитивы
готовы → (2) дерево + анти-цикл → (1) БД-адаптер — отдельный проект со своим
CDC-слоем. Ось 1 в части «мы смотрим» — держать в голове asymmetry чтения
и записи; это главный источник будущих ошибок дизайна.
