# Зеркало стора: leader–follower на примитивах replay

Цель: второй инстанс сервера держит живую копию авторитетного стора и реактивно
обслуживает своих клиентов; порядок записи задаёт только лидер; зеркало можно
вручную повысить до лидера. Кодек остаётся JSON — репликация и сериализация
ортогональны; смена кодека (MessagePack/CBOR) — отдельная задача вне этого плана.

Статус: ВСЕ фазы реализованы и проверены — 62/62 ораклов, реальный браузер: полный failover-круг (лидер убит -> promote кнопкой -> epoch 2 -> узел вернулся зеркалом). План закрыт в 1.0.86.

## Инварианты (рамка всех фаз)

- Одна точка порядка: seq/rev присваивает текущий лидер (роль переезжает через promote).
  Постоянный multi-master и CRDT — вне скоупа; конфликты возможны только в окне failover
  и обрабатываются конфликт-журналом (Фаза 4).
- Follower не применяет команды локально — только форвард лидеру и зеркалирование дельт.
- Дельты применяются строго по порядку; разрыв последовательности — catch-up, а не «пропустить».
- Идемпотентность сквозная: requestId клиента доезжает до лидера без переименования.
- Все порты демо — из диапазона 3100: лидер 3100, зеркало 3101.
- Безопасность межинстансного линка — верхний слой (reverse-proxy / приватная сеть);
  в библиотеке только обычный auth-токен, без специальной механики.

## Что уже есть (переиспользуем, не переписываем)

- `exposeStoreReplay(store, opts)` — стор как replay-источник: кейфрейм + журнал + `getSince` (догон).
- `syncStoreReplay(store, remote)` / `syncStoreReplayRoute` — подписка локального стора на удалённый
  поток с применением `StorePatch`; reconnect-догон уже проверен ораклами.
- `storeReplayAt(storage, at)` — позиционирование по журналу.
- Идемпотентные команды с квитанциями — образец `createWorkboardHost`:
  `receiptKey(account, requestId)`, LRU 2000, конфликт `expectedRevision`.
- Типизированный RPC поверх socket.io + переподключение; server-as-client работает тем же
  клиентским кодом — новый транспорт не нужен.

## Фаза 1 — Follower-режим: зеркалирование чтения

Ядро: инстанс — клиент чужого стора и сервер для своих.

- [x] `createStoreMirror(deps)` (рабочее имя): подключение к лидеру библиотечным клиентом,
      кейфрейм → локальный store, `syncStoreReplay` дельт, контроль непрерывности seq, догон при разрыве.
- [x] Каскад: над зеркальным store — свой `exposeStoreReplay` для клиентов follower'а
      (цепочка replay: leader → follower → браузер, тот же механизм на обоих хопах).
- [x] Статус линка как обычное поле store: `upstream: 'live' | 'catching-up' | 'offline'` —
      фронт показывает его без специального API.
- [x] Оракл: два инстанса в одном тестовом процессе; запись на лидере → сходимость стора
      follower (deep-equal) и реактивная доставка его подписчику.

Критерий: клиент follower'а видит изменения, сделанные через лидера; после обрыва линка —
догон без потерь и без дублей.

## Фаза 2 — Форвард команд

- [x] На follower интерфейс команд тот же, что у лидера; реализация — прокси: команда с исходными
      `account`/`requestId` уходит лидеру, ответ или ошибка возвращаются вызвавшему клиенту.
- [x] Квитанции живут на лидере (уже есть). На follower второй LRU не заводим; допустим лишь
      маленький кэш «ответ в полёте» для ретраев при кратком разрыве follower↔leader.
- [x] Ошибки лидера транслируются как есть — friendly-тексты не переписываются на хопе.
- [x] Оракл: double-submit через follower (ретрай того же requestId) → ровно один эффект;
      конфликт ревизии через follower → тот же текст ошибки, что и напрямую у лидера.

Критерий: клиенту неразличимо, к какому инстансу он подключён.

## Фаза 3 — Поведение при потере лидера

- [x] Чтение продолжается со stale-стором + `upstream: 'offline'`.
- [x] Команды при офлайне лидера — явный быстрый отказ ('leader offline'); очередь не делаем:
      честнее и проще, клиентский ретрай по requestId и так безопасен.
- [x] Reconnect: догон с последнего применённого seq; если журнал лидера уже обрезан —
      полный кейфрейм заново (протокол это умеет).
- [x] Оракл: обрыв в середине пачки дельт → догон → сходимость; обрыв дольше глубины
      журнала → кейфрейм-ресинк.

## Фаза 4 — Ручное повышение (promote), без автоматики

- [x] `promote()`: follower начинает принимать команды и вести журнал сам, стартуя с последнего
      применённого состояния.
- [x] Epoch (term): целое в конфиге запуска, растёт при каждом повышении; подписчики и другие
      фолловеры принимают поток только с большей/равной эпохой — простая защита от «двух лидеров»
      без выборов.
- [x] Команды в полёте при повышении: клиент ретраит тем же requestId уже в нового лидера;
      квитанции нового лидера пусты — допущение зафиксировать в доке (дубль возможен только для
      команд, чей эффект не успел доехать в зеркало; окно = лаг репликации).
- [x] Конфликт-журнал при возвращении старого лидера (окно split-brain): расходящийся хвост его
      журнала не выбрасывается — обе версии сохраняются рядом («зеркало конфликта»), победителя
      детерминированно выбирает бо́льшая эпоха; операции без пересечения перепроводятся как новые
      команды (аналог reorg в блокчейне: транзакции осиротевшей ветки возвращаются в mempool),
      пересекающиеся отдаются приложению на выбор.
- [ ] НЕ делаем: автоматические выборы, кворум, lease — до реальной потребности.

## Риски и решения

- Дубль эффекта при promote (окно лага) — задокументированное допущение ручного failover;
  полностью закрывается только кворумной записью, что вне скоупа.
- Рост журнала — обрезка истории + fallback на полный кейфрейм (опции history/getSince уже есть).
- Эхо-петля: применённая с апстрима дельта не должна возвращаться лидеру — отдельный оракл.
- Кодек: JSON остаётся; единственная подготовка — проверить, что encode/decode патчей замкнуты
  в паре функций replay-wire (только проверить, не менять).

## Открытые вопросы (решить до фазы 1)

1. Имя фабрики: `createStoreMirror` или `createStoreFollower`? (mirror читабельнее, follower точнее по роли)
2. Где живёт `upstream`-статус: полем внутри зеркального store (видно всем клиентам реактивно)
   или отдельным listen-стримом? Склоняюсь к полю store — это «наша фишка» и ноль нового API.

## Отложено (обсудили — вернёмся после Фазы 5)

- Три оси развития синхронизации (направление истины / много узлов / виды передачи) —
  разобраны в отдельной заметке: doc/target/store-sync-directions.md.

- Оптимизация маршрута данных: срезать лишние хопы, когда путь сложный — например, запись
  клиента follower'а прямым линком в лидера вместо пересылки, чтение — с ближайшего инстанса.
  Идея та же, что в route-coordinator relay ⇄ direct: начинаем через посредника, переходим на
  прямой путь, когда он доступен.
- Симметричный multi-master «как в блокчейне» (оба инстанса пишут всегда; форки + детерминированный
  выбор ветки; проигравшие варианты сохраняются как siblings — модель CouchDB/Dynamo). Честная цена:
  подтверждённая запись может позже «откатиться» (reorg), версионные метаданные на каждом элементе,
  глобальные инварианты — только eventual. Берём, только если появится offline-first / гео-сценарий;
  для пары инстансов в одной инфре хватает promote + конфликт-журнала из Фазы 4.
