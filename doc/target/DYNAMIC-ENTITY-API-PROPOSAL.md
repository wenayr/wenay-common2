# Динамический API сущностей: предложение для обсуждения

Статус: предложение, 2026-09-07. Нового публичного API или согласованного имени здесь нет.

Дополнение: создание экземпляра и восстановление проверены в apartment example, см.
[проверку восстановления](CREATED-APARTMENT-RECOVERY.md). Отдельная оценка типов, создаваемых
во время работы: [существующие механизмы и недостающие контракты](RUNTIME-RESOURCE-SCHEMA-ASSESSMENT.md).

## Решение, которое предлагается

Создание объекта должно делать его доступным через существующий API типа. Сам объект не
получает отдельный сервер, набор зарегистрированных маршрутов или постоянно активную подписку.
Удобный клиентский handle по ID можно создавать по запросу; хранить его для каждой строки заранее
не требуется. Первый прикладной пример реализуем существующими командами и проекциями.

Это отвечает двум разным сценариям:

| Сценарий | Предлагаемое поведение |
| --- | --- |
| Пользователь добавил квартиру известного типа | Записать квартиру и связанные данные; действующие команды и views сразу работают с её ID |
| Разработчик добавил новый тип ресурса при сборке | Описать команды, входы, права и проекции; собрать транспорт один раз |
| Пользователь в работающем сервисе создал новый тип со своими полями | Отдельный контракт реестра схем, версий, миграций и runtime-валидации; в первый срез не входит |
| Пользователь загрузил исполняемый код нового API | Отдельная граница dynamic runtime, не следствие появления записи или схемы |

## Что уже делает apartment example

В `experiments/wenay-scaffold/examples/apartments/service.ts` уже существуют:

- `addApartment`: роль host, создаёт квартиру, замок и привязанную device-учётную запись.
- `book`: роль guest, принимает apartmentId, проверяет даты/конфликт и создаёт booking + payment intent.
- `cancelBooking`: принимает bookingId, проверяет владельца и допустимое состояние оплаты.
- `unlock`: принимает bookingId; доступ привязан к бронированию, а не к произвольному lockId.
- Проекции `apartments`, `myBookings`, `ledger`, `hostBoard`, `myLock` разделяют аудитории.

Добавление квартиры не требует нового RPC namespace или нового HTTP route. Это уже подход
«динамические экземпляры, фиксированные операции». Требуется показать и проверить его как
короткий пользовательский сценарий, а не заменять существующие механизмы универсальным CRUD.

## Возможная форма удобного клиента

Сегодня существующая команда получает ID явно:

```ts
await commands.book(requestId, {apartmentId, from, to})
```

Эскиз будущего клиентского удобства, НЕ существующий метод:

```ts
const apartment = client.apartments.at(apartmentId)
await apartment.control.book(requestId, {from, to})
```

Смысл handle — сохранить адрес и передать его в ту же команду. Он не даёт дополнительных прав,
не копирует состояние, не открывает соединение и не запускает подписку. `cancelBooking` и `unlock`
относятся к booking: переносить их на apartment только ради одинакового фасада неправильно.

Граница чтения определяется аудиторией: public apartment, hostBoard и myBookings нельзя слить
в один raw-object view. Клиент получает данные из уже разрешённой проекции. `on`/`events` должны
быть явной поверхностью, подписка возвращает освобождение; удаление/закрытие прекращает доставку.

## Обязательные правила контракта

1. Principal приходит от проверенной сессии. Авторизация операции и актуальное владение проверяются
   на сервере; создание handle не фиксирует права навсегда. RPC оставляет gated initial facade пустым,
   а снижение привилегий прекращает прежние потоки по RPC-AUTH.
2. Идентичность команды остаётся account/requestId с существующими границами receipts. Handle
   не делает скрытых повторов и не обещает атомарного внешнего эффекта или вечного dedup.
3. В текущем примере нет удаления квартиры. Не генерировать delete автоматически: сначала решить,
   что делать с бронированиями, оплатами, замком и device credentials. Предпочтительный первый
   бизнес-путь — явное снятие с публикации, если такой сценарий будет согласован.
4. Если позднее появится удаление и повторное использование ID, старый handle не должен случайно
   адресовать новый объект. Нужен запрет повторного ID либо проверяемая incarnation/generation,
   сохраняемая вместе с данными. Текущие пробы этого протокола не реализуют.
5. Runtime-схема требует runtime-валидации и версии. TypeScript не выводит статический тип схемы,
   которую пользователь создаст после компиляции. Code generation — отдельное осознанное решение.

## Что показывают измерения

В локальной модели 10,000 заранее созданных фасадов добавили около 14.5 MiB по сравнению с общим
доступом; 100 активных подписок стоили примерно одинаково в обоих вариантах. В отдельной HTTP-пробе
регистрация 10,000 маршрутов удерживала около 29.2 MiB, фиксированного обработчика — около 30 KiB.
Эти величины относятся к разным экспериментам и не складываются. Тайминги запросов шумные.

Источники: [локальные фасады](DYNAMIC-ENTITY-API-FEASIBILITY.md),
[HTTP-регистрация](DYNAMIC-ENTITY-HTTP-COST.md). Это аргумент против eager-выделения на каждую
запись, а не предел производительности любых динамических API. RPC schema walk/OpenAPI ещё не измерены.

## Где действительно нужен разговор об API

Для демонстрации создания квартиры и работы по ID расширение библиотеки не требуется.
Новый публичный метод `at(id)` или общий typed binder требует обсуждения, если выносить его в пакет.
Рекомендация — сначала подтвердить удобство на apartment и втором типе, затем решить, оправдан ли
общий helper. Не добавлять в HTTP adapter unregister/replace только ради появления новых объектов.

Конкретный вопрос для решения: нужен ли публичный типизированный handle, который только связывает
ID с существующими командами/проекциями, или достаточно короткой генерации клиента в scaffold?
Рекомендован второй вариант для первого среза; runtime-defined типы рассматривать отдельной задачей.

## Следующий проверяемый шаг

Через существующие команды создать новую квартиру после запуска, увидеть её в разрешённых views,
забронировать по новому ID и проверить изоляцию другого host/device без перезапуска транспорта.
Сохранить существующие payment/lock правила. Сначала найти уже имеющиеся проверки, дополнить только
отсутствующее. Публичные helper-методы и удаление не внедрять в этом шаге.

Проверка этой волны: declarations Command/Store/HTTP, исходные команды/проекции apartments и
канонические RPC-AUTH правила сверены. Менялись только внутренние документы; build/tests не повторялись.
