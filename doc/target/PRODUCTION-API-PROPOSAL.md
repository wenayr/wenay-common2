# Минимальные расширения после SaaS-волн

Статус: предложение для обсуждения, не реализованный или одобренный API.
Первая реализация общей основы описана в [COMMON-LAUNCH-PATH.md](COMMON-LAUNCH-PATH.md).

## Приоритеты

| Потребность | Уже существует | Что действительно требуется |
| --- | --- | --- |
| Общий запуск | Express/HTTP/Socket.IO, RPC и HTTP-адаптеры | Приватный транспортный ресурс scaffold; экспорт библиотеки пока не нужен |
| Повтор запуска FileJob | Command host/receipts; AI requestId | Явный контракт идентичности FileJob; простая внешняя обёртка не закрывает ошибки и права |
| Перезапуск задачи | Store/replay и архивы для других слоёв | Устойчивое намерение, состояние исполнения, владение и запись исхода |
| Горизонтальная запись | Authority, replica, partition tests | Ключ разделения данных и внешнее атомарное fencing, а не увеличение числа читателей |
| Ограниченная память | Лимиты receipts/истории; лимит bytes в примере | Раздельные правила хранения jobs, результатов, request identities и файлов |

## Первый публичный кандидат: идентичность startJob

Сегодня при потере ответа вызывающий не знает, создана ли задача:

```ts
const job = await files.startJob(fileId, input)
// Повтор вызова создаёт новую задачу.
```

Предлагаемый дополнительный фасад (имя и контракт требуют согласования):

```ts
const operationId = savedOperationId
const job = await files.requests.startJob(operationId, {fileId, input})
// После потери ответа повторяется эта операция с тем же ID.
```

Старые методы остаются без изменений. На локальном fragment `startJob` сейчас синхронный;
методы Command.execute асинхронные. Поэтому механическая замена существующего метода на Command
ломает контракт. Новый requests-фасад позволяет явно выбрать Promise и идентичность операции.
Клиент FileJob должен ретранслировать этот блок с сохранением типов; это тоже публичное изменение.

Переиспользовать Command для scope account/requestId, объединения in-flight запросов и копирования
ответов. Права проверять до чтения сохранённого ответа, поскольку Command сам не знает FileJob ACL.
Один ID обозначает первое намерение: другой метод с этим ID отвергается; поведение повторного
ввода с другими аргументами должно быть описано явно (предлагается вернуть первое намерение).

Приёмка: потерянный ответ и повтор дают один job и один запуск runner; параллельные повторы
совпадают; другой account изолирован; отзыв доступа не открывает receipt; старый startJob работает.
Это гарантия определённого окна/жизни host, не восстановление задачи после перезапуска.

## Почему startUpload надо обсуждать отдельно

Command удаляет receipt при исключении, позволяя повтор. Но storage.beginUpload мог выделить
внешний объект и потерять ответ. Повтор после этой ошибки может выделить второй объект.
Нельзя назвать такую обёртку безопасной идемпотентностью.

Возможный будущий `requests.startUpload(id, request)` требует состояния неизвестного исхода:
после входа в storage сохранить результат/неопределённость, не выполнять эффект повторно вслепую.
Ошибки валидации до эффекта могут оставаться повторяемыми. Устойчивый storage-side operation key
и lookup/reconciliation — отдельный контракт ресурса. Сначала выбрать требуемую гарантию.
Истёкшую upload-инструкцию обновлять для того же fileId, не создавать новую загрузку.

## Retention — часть гарантии

Command имеет ограниченное хранение receipts; pending не вытесняются. После удаления записи
нельзя обещать подавление повторного эффекта. Сохранившийся job должен сохранять связь с операцией
либо политика обязана явно ограничивать окно повторов. Нужны отдельные границы числа выполняемых
операций, завершённых задач, bytes и ключей повторов; один TTL для всего недостаточен.
Отдельно определить исход при достижении лимита и способ увидеть оставшийся объём.

Не предлагать durable receipts как замену durable jobs. Восстановленный receipt с ID задачи,
которой больше нет, не является восстановленным результатом.

## Устойчивые задачи: следующая самостоятельная граница

До выбора методов сформулировать протокол: записать намерение → принять работу владельцем →
выполнить эффект → атомарно записать исход → опубликовать результат. Проверить сбой между каждой
парой шагов. Возобновление вычисления и повтор внешнего платежа/вызова модели имеют разные правила.
Worker должен иметь fencing/lease на конечном ресурсе; отмена и потеря lease не равны откату эффекта.
Выбор конкретного хранилища и executor делать на одном документном сценарии, не строить общий
workflow-движок заранее. Внешнее развёртывание требует отдельной авторизации.
