# Передача артефактов (динамический код) между узлами — дизайн-заметка

Контекст: артефакты = динамический код (HTML/JS), создаваемый на лету; их надо
уметь передавать по сети между узлами и участниками — БЕЗОПАСНО. Хорошая
новость: подсистема artifact уже разложена по правильным слоям, и передача
ложится на неё одним новым портом, без перестройки.

Что уже есть (src/Common/artifact):
- Каталог — `ArtifactStore {artifacts: Record<id, ArtifactRecord>}` — это обычный
  Store: descriptor/owner/state/retention. УЖЕ store-shaped.
- Байты — за `ArtifactStoragePort` (open → короткоживущий авторизованный URL);
  `storageKey` живёт только на сервере, в Store и RPC не попадает.
- Исполнение — `createArtifactFrame`: sandboxed-iframe, `sandbox="allow-scripts"`
  и ничего больше, origin-pinned (allowedOrigins), БЕЗ моста к родителю.
- Политика — canRead/canRevoke/canRegister, по умолчанию только владелец.

## Принцип: три слоя врозь

1. **Каталог** (мелкое, горячее) — реплицируется как любой store: replay-линия,
   createStoreFollower, каскад. Запись в каталоге = «артефакт существует»,
   НЕ право его читать.
2. **Байты** (крупное, холодное, immutable) — НЕ через журнал (журнал для
   мелких патчей); едут по ссылке/запросу, лениво, с кэшем на узле.
3. **Исполнение** (опасное, локальное) — только песочница у конечного клиента.
   Сервер/узел динамический код НЕ исполняет никогда.

## Безопасность по построению (а не церемонией)

1. **Контент-адресация**: версия артефакта = hash его байтов (descriptor.version).
   Получил байты → сверил hash → подмена по дороге невозможна физически.
   Версии immutable; обновление = новая версия + сдвиг указателя в каталоге;
   журнал каталога даёт историю и откат бесплатно.
2. **Песочница без полномочий**: allow-scripts и всё; никакого eval/динамического
   import в контексте узла или страницы. Способности артефакту выдаёт ХОСТ
   через будущий узкий postMessage-мост (capability injection): код просит —
   хост решает. (Комментарий в artifact-frame это уже предвидит: «no parent
   bridge; app-specific capabilities need a separate protocol».)
3. **Право чтения не реплицируется**: политика canRead и storageKey остаются
   у узла-хранителя; каталог разъезжается по сети, а «кому открывать» каждый
   узел решает своей политикой + короткоживущими тикетами (как сейчас).
4. **Авторство**: пока хватает hash + доверия к линии (транспорт лидера);
   подпись автора поверх hash — опция на потом, когда появятся чужие узлы.

## Передача = сетевой порт хранения

- На follower-узле ставится `ArtifactStoragePort` с логикой: «байты по hash:
  локальный кэш → спросить источник (лидера / по дескриптору источника из
  store-sync-directions.md) → проверить hash → закэшировать». open() после
  этого всегда локальный — короткий URL со своего узла.
- Транспорт байтов — любой из имеющихся, по оси 3: file-jobs (тикеты и лимиты
  уже есть), socket relay, WebRTC direct для p2p.
- P2P участник→участник: регистрация в каталоге + байты напрямую с проверкой
  hash; каталог даёт адресуемость, песочница получателя — безопасный запуск.

61/61 полного прогона, реальный браузер: артефакт лидера открыт у зеркала и наоборот.

       политика на кромке, revoke-форвард) + репликация каталога через createStoreFollower.
3. [x] Демо: AI-артефакт, созданный на любом инстансе, открывается на другом — каталог мгновенно
       по replay, байты лениво по hash, раздача с локального sandbox-origin каждого узла;
       форвард-регистрация с приёмной сверкой хэша (зеркалу не верим на слово).
4. [ ] Позже: capability-мост, подпись автора, p2p direct-доставка.

## Не делаем

- Server-side исполнение динамического кода (изолированные воркеры) — отдельный
  мир, не сейчас; узлы только хранят и раздают байты.
- PKI/подписи — до реальной потребности в недоверенных узлах.
