# 2.16.0 — consumer bridges: loopback testing kit, storeExternal, value-semantics contract

Release theme: the core did not move — this release builds the bridges consumers kept rebuilding
by hand: an exported connection-lifecycle loopback pair for testing facades, the
useSyncExternalStore tuple over Store paths, and the Store reactivity contract pinned as an
executable spec and stated in the docs.

## RPC testing kit: `createLoopbackSocketPair`

- New export from `wenay-common2` / `wenay-common2/rpc` (`src/Common/rcp/rpc-inproc.ts`):
  `createLoopbackSocketPair({delivery?: 'micro'|'sync'}) -> {client, server, kill, setOnline, online}`.
  Same detached in-proc wire as `createInProcSocketPair` (JSON round-trip + native binary
  attachments, no identity leaks), plus the two facts a transport test needs to stage:
  `kill()` — definitive socket death, `'disconnect'` on both ends, delivery over;
  `setOnline(false)` — silent-loss window (frames drop, nobody is told), `setOnline(true)` resumes.
- Consolidates the ad-hoc `createLoopback` copies living in 9+ spec files; existing copies stay
  untouched (churn), the export is canonical for new code and for consumers testing their own
  facades without socket.io.
- Docs fix: the rare-docs line advertising this layer named a non-existent `createRpcServerInProc`;
  it now documents the real `createRpcInProc` / `createInProcSocketPair` / `createLoopbackSocketPair`.
- Spec: `src/Common/rcp/rpc-inproc.spec.ts` (end-to-end facade + Listen + binary over the pair,
  offline window, kill semantics, sync delivery, wire detachment) — wired into `npm test` /
  `test:all` as `test:rpc-inproc`.

## Observe: `storeExternal` — the React 18 external-store tuple, zero React dependency

- `Observe.storeExternal(nodeOrStore) -> {subscribe, getSnapshot}` over any `{on, snapshot}` source
  (a `store.node` path or the Store root). `getSnapshot` identity is stable between changes and
  recomputed lazily on the first read after a change fact — the exact `useSyncExternalStore`
  contract, so React consumes a Store path without a re-render loop and the library stays
  framework-free. (`src/Common/Observe/store-external.ts`.)
- `subscribe()` itself invalidates the cache: a change landing in the render→subscribe gap is
  caught by React's post-subscribe re-read (without this the component froze on the stale
  snapshot); one subscriber leaving no longer disturbs the peers' cached identity. Spec:
  `src/Common/Observe/store-external.spec.ts` (`test:store-external` in `npm test` / `test:all`) —
  gap invalidation, identity stability between changes, peer-unsubscribe isolation.

## Observe: reactivity contract pinned

- New spec `src/Common/Observe/store-value-semantics.spec.ts` (`test:store-values` in `npm test` /
  `test:all`) pins the table: plain objects/arrays reactive at any depth (including array in-place
  mutation and coalescing to one fact per drain window); rich values
  (Map/Set/Date/TypedArray/class instances) are VALUES — replacement visible, in-place mutation
  invisible by design, prototypes preserved, snapshots still deep-clone them with full semantics.
- The rule is now stated in `doc/wenay-common2.md` §Observe (it previously lived only in
  `reactive.ts` internals, while the RPC docs advertise Map/Set as first-class — the gap that made
  the wrong expectation easy).

## HTTP facade OpenAPI: 3.1.0 + real tuple bodies via `argSchemas` (demo incubator)

- `demo/http-openapi.ts` now emits OpenAPI **3.1.0** unconditionally (was 3.0.3) and gains optional
  `argSchemas?: Record<route, JsonSchema[]>`: a route present there documents its POST body args as
  a REAL fixed tuple (JSON Schema 2020-12 `prefixItems`, `items: false`, exact min/max) instead of
  the generic bounded array — named fields with real types reach standard consumers
  (openapi-typescript emits `args: [string, {itemId: string, from: string, to: string}]`;
  swagger-ui-dist 5.x renders the 3.1 document). Routes without `argSchemas` are unchanged.
- Oracle `replay/http-openapi.test.ts` 25 -> 29 checks: tuple documented in both body variants,
  non-tuple routes keep the generic array + example, and the live leg proves the served 3.1.0
  document and that a tuple-shaped POST is exactly what the server accepts.
- Scaffold incubator (`experiments/wenay-scaffold`, unpublished): commands can declare a
  runtime `input` schema (`template/input-schema.ts` — tiny DSL: scalars, `'?'` optional, enum,
  array, nested object) that is the single source of automatic validation before `validate()`,
  the inferred TS input type (`schemaCommand`), and the OpenAPI body tuple; rental example adopts
  it end-to-end (self-checks 24/24 and 23/23, incl. an openapi-typescript field-level proof).

## Docs: two recipes (rare docs, RPC section)

- **Runtime input validation at the RPC boundary**: the `hooks.onRequest` seam with a per-path
  validator table (types erase; `RpcLimits` bounds volume, values are the application's).
- **Store state schema evolution across deploys**: additive change = deploy and nothing else;
  breaking change = bump `lineId` (stale cursors → one fresh keyframe, never a mixed-shape
  mirror); version the shape inside the data for rolling-deploy coexistence; never persist a naked
  seq without its lineId.
