# 2.12.1

Fixes a type regression introduced in 2.12.0: a replay member reached through the hub lost
`line` / `since` / `keyframe`.

- **`IsReplayMember` now reads the journal tail in both of its spellings.** A server member
  exposes `getSince`; once `DeepSocketListen*` has projected it, the client surface spells the
  same thing `since`. `createRpcClientHub` composes two passes —
  `ClientAPIAll<DeepSocketListenSmart<T>>` — so on the second pass the detector missed, and the
  `IsListenMember` branch added in 2.12.0 claimed the member and collapsed it to a plain
  subscription. Consumers saw `Type 'SocketListenMember<…>' is missing the following properties
  from type 'ReplayRemote<…>': line, since, keyframe`. Reading both spellings makes the
  projection idempotent, which is what composing two passes requires. Runtime was never
  affected; the detector is type-level only.
- **`type-tests/rpc-replay-member-idempotence.ts` covers the composition, not just one pass.**
  The 2.12.0 test applied two passes but to a plain Listen member, so the replay path was never
  exercised twice — which is exactly why the regression shipped. The new test pins the hub lane,
  the strict lane, `DeepSocketListen` as the inner pass, and a third application, and keeps a
  `@ts-expect-error` proving a plain Listen member is still NOT treated as a replay remote.
  Verified by negative control: with the 2.12.0 detector restored it fails at all four sites.

Reported against a real application by the consumers of `wenay-react2`, with the analysis that
located it: two projections composed, one detector that knew only the inner one's input.
