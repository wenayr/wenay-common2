# 2.12.0

A subscription reached through the typed client lane is finally typed, and three measured
allocations leave the packet path.

- **`ClientAPIAll` / `ClientAPIStrict` project a plain Listen member to its real surface.**
  The object recursion used to meet `on` as an ordinary method and map it to
  `Promise<DeepDataOnly<SubscriptionHandle>>`; the handle is callable, `DeepDataOnly` erases
  `Function`, and the member collapsed to `Promise<never>` — which is why
  `doc/wenay-common2.md` told readers to cast the whole facade to `DeepSocketListen`. The new
  `IsListenMember` branch sits beside the existing `IsReplayMember` one and yields exactly the
  shape that cast produced, so the cast is now redundant rather than replaced, and existing
  casts keep compiling. `type-tests/rpc-listen-projection.ts` pins it, including a
  `@ts-expect-error` that fails if the branch is ever removed.
- **`utf8ByteLength` stops allocating a copy of every message to answer one number.**
  `TextEncoder.encode(value).byteLength` built a `Uint8Array` the size of the whole payload on
  each batched packet; Node counts the same bytes with `Buffer.byteLength`. The browser keeps
  the encoder, where the alternative is a surrogate-aware loop that would have to match
  `TextEncoder` byte for byte.
- **`offerTick` remembers the last shape instead of re-deriving it every tick.** A tick stream
  repeats one shape for thousands of packets, and each one paid `slice().sort()` plus
  `JSON.stringify` for an answer that had not changed. Incoming keys are compared in order —
  an ordered match cannot produce a different sorted signature, and keys that passed
  `isSafeKey` stay safe — so the memo can only skip work, never decide differently. A
  reordered object misses and takes the full path.
- **The live replay channel decodes its own bytes with `decodeTrusted`.** The wire is produced
  by our encoder one line above and crosses no boundary, so the untrusted reader's per-key
  work was spent on input that cannot be hostile. Limits are unchanged.

Measured on `experiments/rpc-perf-2026-07`, family `flood`, 9 runs at triple load. Configurations
the change touches, p50 per round: `request-batch` 1.534 → 1.331 ms (−13.2 %), `defaults`
1.536 → 1.344 ms (−12.5 %), `no-compact` 1.461 → 1.344 ms (−8.0 %) — all three with
non-overlapping confidence intervals. Configurations it cannot touch did not improve:
`no-callback-batch` +3.5 %, `plain-json` +2.5 %, both inside the noise band — which is what rules
out a machine-wide drift. `no-callback-batch` showing nothing is also the attribution: the
batcher path is where the byte-count allocation lived. CPU per message moved the same way in all
four touched configurations and the other way in both untouched ones, but the per-configuration
intervals are too wide to claim any single figure. The replay-channel change is not exercised by
this stand at all and is claimed on construction only, with no share of these numbers.
