# 2.9.0

A third replay retention mode and a resumable-stream recipe. No behavior changes without the
new module.

- **`openFsSpillJournal(file, {history, maxBytes})` (wenay-common2/server) — RAM-first window,
  disk only on eviction.** Between "bounded RAM ring" (loses history past the cap) and the
  always-on durable journal (pays steady-state SSD writes): recent history lives in a RAM ring,
  and only what the ring evicts is appended to disk — a steady state where every consumer sits
  inside the window costs zero disk writes, while a client back from a long absence still gets
  its exact tail up to `maxBytes` of spilled prefix. Disk is two rotated JSONL segments (prune
  drops the older segment — a 1 GiB budget never costs a 1 GiB rewrite), not mirrored in RAM;
  reads open the file only on a cache-miss `getSince`. Wires into any line as memory-outside:
  `exposeStoreReplay(store, {...spill.line})` / `replayListen(base, {current, ...spill.line})`.
  Deliberately not restart-durable (a dead process's RAM suffix leaves an unfillable gap —
  `open()` starts a fresh lifetime; restarts remain `createDurableStoreReplay`'s job) and
  best-effort under disk trouble: a failed spill shrinks the window to RAM and old readers
  degrade to the keyframe reset the wire already knows, never to a broken tail.
  Oracle: `replay/fs-spill-journal.test.ts`.
- **rpc.md: "resumable flow stream" recipe** next to `flowCallback`: a flow stream is
  call-scoped, so the resume point is a method argument (`{from}`) — only the client knows what
  it durably consumed; the server keeps nothing. With the boundary stated: live events that must
  survive absence belong to a replay line, not to this recipe.
