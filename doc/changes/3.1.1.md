# 3.1.1

Store engine memory and honest checks. No API, wire-format or documented-behavior change.

## Store engine

- A reactive node is its own proxy handler: the traps live once on a shared prototype instead of
  eight closures per node, subscriber and child collections are created on first use, and the path
  is derived from the parent chain instead of stored. Per node: 1,765 → 189 B (100k flat keys),
  1,794 → 199 (nested), 1,824 → 232 (array rows); creation 1,869 → 479 ns, a hot read 610 → 467 ns,
  a write 752 → 515 ns (795 → 557 with `onUpdate`, 2,371 → 1,866 with `onUpdatePaths`).
  Specs: `reactive-node-heap` (failed at 1,765 B, budget 384) and `reactive-surface`, 222 probes of
  the proxy's visible behavior recorded from 3.1.0 (reflection, JSON, freeze/seal, array length,
  detached subscribers, depth limits): identical. Debugging only: `util.inspect` with
  `showProxy: true` shows the node as the handler, and stack frames read `Node.get`.

## Examples

- Every async entrypoint of an example's `npm run check` ends through `runCheck(main)`
  (`run-check.ts`, shipped in each example). Before, an await that could never settle exited 0 with
  the later checks unrun, and one waiting with a server open never exited (shown on
  `hosting/public-address.ts`); now both exit 1 with a message. The deadline is 120 s, the slowest
  check takes about 13 s. The example generator refuses a check entrypoint without it.

## Docs

- RPC-AUTH: the expiry or revoke notice (`Pkt.AUTH`) and the downgrading `Pkt.MAP` are separate
  packets; over long-polling they can land in different responses, so treat a session as
  downgraded once `auth()` answers `ok: false`, not on the notice alone.

## Repository

- `npm test` type-checks the oracle directories (`tsconfig.oracles.json`): 138 accumulated errors
  fixed. Two checks were vacuous and now test what they claim: `store-patch-safety` saw a decode
  failure where it meant a materialization failure, and `critical-fixes` awaited a property that
  does not exist.
- CI on Linux, red for many releases, reproduced in a `node:24` container. Two defects, both in
  the checks, not the library: `replay-binary-decode-cost` timed the building of its hostile
  frame (a 1 MB spread into JS arrays, up to 0.9 s on Linux) and paid that garbage inside the next
  timed decode; the decode itself takes 4-14 ms. It now times only the decode, takes the fastest of
  three runs and bounds a leaf flood by its ratio to the largest legal frame (negative controls: a
  quadratic scan and a budget checked after the whole frame both fail). `test:package` ran
  `node bin/esbuild`, which is a native binary on Linux; it uses the esbuild API.
- Demo stand, Lab → Service tokens: real service leaders in a per-tab sandbox show the 3.0.1 token
  rules and name the deciding layer at every step (a handshake-named account gets no token,
  server-side issuance after the application's own login, `access.login`, operator revoke).
  Oracle: `oracle/realsocket/service-token-stand.spec.ts`.

## Found, not changed (public surface, waiting for a decision)

- Service leader: `createServiceLeader` has no token-lifetime option (every token lives the codec's
  default 15 minutes); the per-socket mounting of a leader (name wrap, `attach`, ungated fragment)
  is not exported, so a host sharing its Socket.IO server copies it (the rental example and the
  stand's Service tokens panel do); the deny list forgets an account only through
  `identity.login(account)`, which also mints a token.
- Types narrower than the runtime: `StoreReplayRemote` accepts only V2 batch tuples, although
  `syncStoreReplay`, `syncStoreReplayRoute` and `createOfflineStore` also decode the plain
  batch-event remotes that `conflateReplay(exposed.replay)` produces; `createStoreManager` accepts
  only `ManagedStoreResource<any>`, so a resource typed with its state does not compile; the
  `strict` facade of an untyped client (`ClientAPIStrict<any>`) cannot be navigated while its
  `func` is `any`. The oracles mark each with a `// library type:` cast.
- Windows CI failed intermittently about four minutes into `release:verify` in earlier runs; all
  three jobs (Ubuntu Node 20 and 24, Windows Node 24) passed on this release's code, but without a
  log of a failed run the cause is not established (possibly the timing fixed above).
